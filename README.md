# Security — Hartwell Labs

This is where the security contact lives, in one place, rather than in the same
three repositories with three slightly different versions of it.

The standard address for this is

    https://github.com/Hartwell-Labs/.well-known/security.txt

and it is worth being honest about why that URL does not resolve here: serving
it from the organisation requires private vulnerability reporting configured at
organisation level, which is not something this account can turn on through the
API. Google, Microsoft and GitHub itself all return 404 there too. The real
address that works is the one on our own domain:

    https://hartwell-labs.pl/.well-known/security.txt

## Reporting a vulnerability

**Do not open a public issue.** Not in any repository, not in a discussion, not
in a pull request.

- **https://hartwell-labs.pl/security/** — the full policy, and what happens next
- **security@hartwell-labs.pl** — reaches a person
- **important@hartwell-labs.pl** — the same mailbox, the address the website's
  own `security.txt` has always published

All three land in the same place. They are listed separately because a
researcher should not have to guess which of them is current.

## What we are running

The organisation publishes security software, so assume the interesting findings
are in:

| | |
|---|---|
| `talus-process-monitor` | eBPF detection agent, MIT. Reads syscall traces and decides what looks like mass encryption. |
| `linux-aegis` | A Linux Security Module. Patches the kernel — treat findings as kernel findings. |
| `quantum-shield` | Post-quantum file encryption. ML-KEM-768 and AES-256-GCM. |
| `fortis` | Chain-of-trust attestation, bare-metal RISC-V. Measured boot. |
| `scryer-core` | Intelligence platform. Dual licensed; the commercial terms exist for a reason. |

`talus-enterprise` is not public and is not listed here. That is deliberate: it
holds the code that can end a process, and publishing its existence with a link
would be pointless. If you believe you have found a vulnerability in it, the
contact addresses above are the same ones.

## What happens after you report

| Stage | Target |
|---|---|
| Acknowledgement | 2 business days |
| First assessment | 7 days |
| Fix or mitigation plan | 30 days from the report |
| Disclosure | Coordinated with you |

You are credited in the advisory unless you would rather not be. Reporting a
real problem does not get you paid, because there is no bounty programme here —
but it does get it fixed, and you get told when.

## Out of scope

- Findings that need physical access to the machine
- Denial of service against our own infrastructure
- Missing hardening headers on a marketing site
- Reports generated by a scanner with no demonstration of impact

The last one matters: we run the same scanners you do, on our own repositories,
continuously. A finding that arrives the morning after a Dependabot run and has
no reproduction behind it costs a person's time and fixes nothing.
